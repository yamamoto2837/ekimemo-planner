# 駅メモ全駅アクセス支援アプリ 要件定義書

Oct 19, 2026 · @sena

## 目的とゴール

残り約3,000駅を、どの順番でどう回るかを決めるためのアプリを作る。

利用者はアクセス済み6,000駅以上の終盤プレイヤー。この段階の課題は「次にどこへ行くか」ではなく「散らばった取りこぼしをどう束ねるか」に移っている。近場の未アクセス駅はすでに尽きており、1駅あたりの移動コストが上がり続ける局面にある。

解決したいこと

1. 取りこぼしの発見 — あと数駅でコンプする路線が、全国に埋もれて見えなくなっている
2. 遠征単位の計画 — 1回の遠征で回る範囲と順序を、鉄道の経路に沿って決めたい
3. 進捗の俯瞰 — 路線別・地域別に、どこがどれだけ残っているかを一覧したい

解決しないこと

アクセスの記録そのものは駅メモマップ2が担う。本アプリは記録を読み込む側であり、置き換えを狙わない。

## 前提条件と制約

ゲームへの自動操作・自動取得は行わない。本アプリはゲームの外側で動く計画支援ツールであり、駅メモのサーバーには一切アクセスしない。

| 項目 | 前提 |
| --- | --- |
| 進捗の入力 | 駅メモマップ2のデータエクスポート文字列を手動で貼り付ける |
| 更新頻度 | 遠征の前後に手動で取り込み直す（リアルタイム同期はしない） |
| 主な移動手段 | 鉄道中心。ルート算出は路線の接続を前提とする |
| 利用環境 | 自宅PC（遠征計画）と出先スマホ（当日確認）の両方 |
| 想定残り駅数 | 約3,000駅（アクセス済み6,000駅以上） |
| 駅マスタ | 駅データ.jp の無料CSV |

この制約から導かれる設計判断がひとつある。進捗が手動更新である以上、アプリ側は「最後に取り込んだ時点のスナップショット」を扱う。当日のアクセス結果を即座に反映する機能は作らず、代わりに取り込みを1分以内に終えられる手軽さを優先する。

## データ設計

駅メモマップ2のエクスポートは駅データ.jpの駅コードをJSON配列で並べたものだった。自前の駅マスタを作る必要はない。

### エクスポート形式の解析結果

サンプル201件（重複なし）を解析したところ、197件が7桁、4件が4桁だった。7桁IDを先頭5桁でグループ化すると23路線分に分かれ、各グループは24駅・23駅・21駅といった自然な分布を示した。

駅データ.jpの仕様では、駅コード（station\_cd）は整数7桁、路線コード（line\_cd）は基本5桁で「鉄道コード + エリアコード + 連番」という採番ルールを採る。サンプルの構造はこれと一致する。

### 駅マスタの構成

[駅データ.jp](https://ekidata.jp/) の無料CSV3種を使う。利用には無料アカウント登録が必要。

| ファイル | 内容 | 本アプリでの用途 |
| --- | --- | --- |
| 駅データ | 駅コード、駅名、路線コード、都道府県、緯度経度、状態 | 未アクセス駅の特定と地図表示 |
| 路線データ | 路線コード、路線名、事業者 | 路線別の集計と表示 |
| 接続駅データ | 隣接する駅コードの組 | 鉄道グラフの構築とルート算出 |

接続駅データが本アプリの要になる。駅同士の隣接関係が取れるため、直線距離ではなく実際の線路に沿った経路を計算できる。鉄道中心の移動という前提に直接効く。

### 名寄せ（最重要）

駅データ.jpは同一の駅でも路線ごとに別の駅コードを振り、それらを駅グループコード（station\_g\_cd）でまとめる。一方、駅メモは1つの駅を1つとして数える。

したがって達成率の分母・分子はいずれも駅グループコード単位で算出する。駅コード単位で数えると、乗り入れの多い都市部の駅が重複計上され、達成率が実際より低く出る。

### 絞り込み

駅データには状態（e\_status）があり、0が運用中、1が運用前、2が廃止を表す。

ただし運用中のみに絞るのは誤り。駅メモには廃駅の一部が登録されたまま残っており、それらも全駅アクセスの対象に含まれる。0で機械的に絞ると、対象駅が実際より少なく算出される。

方針として0と2の両方を候補に残し、2の駅には廃駅フラグを立てて区別する。どの廃駅が駅メモの対象かは、次の2通りで判別する。

1. アクセス済みかつ e\_status が 2 の駅 — 駅メモに存在する証拠になる。6,000駅超のエクスポートから自動抽出できる
2. 未アクセスの廃駅 — 自動判別ができない。駅メモマップ2の表示と突き合わせ、手動で対象を確定する

1（運用前）は除外する。開業前の駅は駅メモにまだ登録されていない。ただし開業時に新駅として加わるため、マスタ更新時の監視対象とする。

### 未解決：4桁のID

サンプルに含まれた 1000・1001・1002・1003 は、どの体系にも当てはまらない。駅データ.jpでは新幹線駅は6桁、新幹線の路線コードは4桁であり、いずれとも異なる。

駅データ.jpでは新幹線駅のデータが有料扱いのため、駅メモマップ2が無料データに含まれない駅へ独自IDを振った可能性が高い。4件と少数なので、駅メモマップ2の地図上で該当駅を特定し、手動の対応表で補う方針とする。

## 機能要件：MVP

MVPの価値は「取りこぼし回収リスト」が握る。終盤では、あと数駅でコンプする路線を拾うのが最も費用対効果が高いが、全国に散らばっているため目視では見つからない。

| # | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| F1 | 進捗インポート | 駅メモマップ2のエクスポート文字列を貼り付けて取り込む | 必須 |
| F2 | 取りこぼし回収リスト | 残り駅数が少ない順に路線を並べる。残り1駅・2駅・3駅で絞り込める | 必須 |
| F3 | 路線別残り駅一覧 | 路線を選ぶと、路線上の駅順で全駅を表示し未アクセス駅を色分けする | 必須 |
| F4 | 地域別進捗 | 都道府県別の達成率と残り駅数を一覧する | 必須 |
| F5 | 地図表示 | 未アクセス駅を地図上にピン表示する。都道府県・路線で絞り込める | 必須 |
| F6 | 現在地から近い未アクセス駅 | 出先で、近い順に未アクセス駅を並べる | 推奨 |

F3で路線上の駅順に並べるのが重要になる。「路線の端が丸ごと残っている」のか「中間の1駅だけ抜けている」のかで、遠征の組み方がまったく変わるためである。並び順は駅データの並び順（e\_sort）と接続駅データから構成する。

集計の主軸は路線とする。F2・F3を路線単位で組み立て、都道府県別（F4）は俯瞰用の補助に位置づける。

集計単位は路線コード、達成率の分母は駅グループコードで名寄せした値を使う。

駅データ.jpの路線区分が駅メモ側の括りとずれる場合は、路線名を駅メモの表記へ寄せる対応表を持つ。路線を主軸とする方針自体は変えない。

### MVPに含めないもの

巡回順序の自動算出、レーダー圏計算、遠征プランの保存は次段階に回す。まず進捗が正しく読み込まれ、残りが正しく見えることを確認してから拡張する。

## 機能要件：拡張

| # | 機能 | 内容 | 段階 |
| --- | --- | --- | --- |
| F7 | 巡回順序の算出 | エリアを指定し、未アクセス駅を鉄道経路に沿って回る順序を出す | 第2段階 |
| F8 | 遠征プラン保存 | 日付・対象駅・順序を保存し、実行後に結果を記録する | 第2段階 |
| F9 | レーダー圏計算 | ある地点から近い順にn駅取れる前提で、効率の良い立ち位置を算出する | 第3段階 |
| F10 | 新駅・廃駅の差分検知 | 駅マスタ更新時に、コンプ済み路線へ新駅が加わったら知らせる | 第3段階 |

### F7の設計方針

鉄道中心という前提から、直線距離による巡回セールスマン問題は採用しない。線路がない方向に最短経路が引かれ、実行不可能な順序が出るためである。

代わりに接続駅データから鉄道グラフを構築し、駅間の移動コストをグラフ上の経路長で測る。その上で最近傍法により初期順序を作り、2-opt法で改善する。エリアを区切れば対象は50〜200駅程度に収まり、この規模なら計算は一瞬で終わる。

乗換時間や運行本数までは考慮しない。それらを入れると必要なデータ量が跳ね上がる割に、机上の計画としての精度向上は限定的なためである。

### F9を後回しにする理由

レーダーは移動量を大きく削る仕組みであり、攻略効果そのものは大きい。ただし「任意の地点から近い順にn駅」を求めるには、駅の最寄り領域（ボロノイ分割）を扱う必要があり、実装の難度がMVPの他機能と大きく異なる。基本機能が安定してから着手する。

## 画面構成

PCとスマホで用途が分かれる。PCは一覧と地図を並べて遠征を練る場、スマホは現在地まわりを確認する場として設計する。同一のWebアプリで、画面幅によって表示を切り替える。

| 画面 | 役割 | 主な利用環境 |
| --- | --- | --- |
| ダッシュボード | 全体の達成率、残り駅数、取りこぼし回収リストの上位 | PC |
| 路線一覧 | 残り駅数順に路線を並べる。絞り込みと並べ替え | PC |
| 路線詳細 | 路線上の駅順に全駅を表示し、未アクセス駅を色分け | 両方 |
| 地図 | 未アクセス駅のピン表示。都道府県・路線で絞り込み | 両方 |
| 近くの未アクセス駅 | 現在地から近い順の一覧 | スマホ |
| データ取り込み | エクスポート文字列の貼り付けと取り込み結果の確認 | PC |

取り込み画面では、読み込んだ件数と、マスタに存在しなかったIDの一覧を必ず表示する。4桁IDのような想定外のデータを黙って捨てると、達成率がずれた原因を追えなくなるためである。

## 技術構成

サーバーを持たない静的Webアプリとする。個人利用で、データも手元にしか無いため、サーバーを立てる理由がない。運用費もかからない。

| 要素 | 選定 | 理由 |
| --- | --- | --- |
| 形態 | 静的Webアプリ（HTML / CSS / JavaScript） | サーバー不要。同一URLでPC・スマホ両対応 |
| 公開先 | GitHub Pages | 無料。Claude Codeからの更新と相性が良い |
| 進捗の保存 | IndexedDB | 駅マスタ約1万件と進捗を扱う。ローカルストレージでは容量が不足する恐れがある |
| 駅マスタの同梱 | JSONに変換してアプリに同梱 | 毎回CSVを読ませない。更新は月次で手動 |
| 地図 | Leaflet + OpenStreetMap | 無料。駅メモマップでも採用実績がある |
| ルート計算 | 最近傍法 + 2-opt（鉄道グラフ上） | エリア単位50〜200駅なら実用的な速度で解ける |

駅マスタはCSVのまま読み込まず、ビルド前にJSONへ変換して同梱する。変換時に駅グループコードでの名寄せと運用中駅の絞り込みを済ませておけば、実行時の処理が軽くなる。

フレームワークは使わない。素のJavaScriptで足りる規模であり、プログラミング未経験からの出発では、学ぶ対象が少ないほうがコードを読めるようになるまでが早い。

## 開発の進め方

動くものを早く作り、小さく積み上げる。各ステップの終わりに必ず画面で確認できる状態にしておくと、どこで狂ったかを特定しやすい。

1. 準備
   - 駅データ.jpに無料アカウントを登録し、駅・路線・接続駅の3ファイルをダウンロードする
   - 駅メモマップ2でエクスポートを実行し、全文をファイルに保存する
2. データ検証（コードを書く前に）
   - エクスポートの全IDが駅マスタに存在するか突き合わせる
   - 4桁IDが何駅かを確定させる
   - 駅グループコードで名寄せした全駅数が、駅メモの公称駅数と近いか確認する
3. マスタ構築
   - CSVをJSONへ変換する。名寄せと運用中絞り込みを適用する
   - 路線ごとの駅順を接続駅データから組み立てる
4. MVP実装（F1〜F5）
   - 取り込み → 集計 → 一覧 → 地図の順に作る
5. 公開
   - GitHub Pagesに置き、スマホからの表示を確認する
6. 拡張（F6以降）

### Claude Codeの使い方

ステップ2が最も重要で、ここはClaude Codeが得意とする作業にあたる。「このCSVとこのJSONを突き合わせて、一致しないIDを一覧にして」と伝えれば、スクリプトを書いて実行し、結果まで出してくれる。

本要件定義書をプロジェクト直下に置き、`CLAUDE.md` から参照させると、毎回の説明が要らなくなる。

1回の指示は1ステップに留める。まとめて頼むと、どこで意図とずれたかを追えなくなる。未経験からの出発では、小さく頼んで都度動かすほうが結果的に早い。

## 未確定事項とリスク

| # | 内容 | 影響 | 対応 |
| --- | --- | --- | --- |
| R1 | 4桁IDの正体が不明 | 大。209件（全体の3%） | 新幹線駅データとの照合、または駅メモマップ2側の対応データを探す。1件ずつの手作業は不可能な件数 |
| R2 | 駅メモとデータ.jpの駅リストが一致しない | 大。達成率が狂う | ステップ2で全件突き合わせ、差分を一覧化してから設計を確定する |
| R3 | エクスポート全量を未確認 | 中 | サンプル201件は一部。全文での再検証が必要 |
| R4 | 新幹線駅が無料データに含まれない | 中 | 差分の規模を確認し、手動補完か有料データかを判断する |
| R5 | 駅マスタの月次更新 | 小 | 駅メモマップ2の更新告知を見て手動で更新する |

R2が最大のリスクになる。駅データ.jpの路線区分は鉄道要覧と異なるという指摘が過去にあり、駅メモ側の路線の括りとずれる可能性がある。路線単位の集計（F2・F3）は、この差分の大きさ次第で見せ方を変える必要が出てくる。

いずれもステップ2の突き合わせで実態が判明する。設計を固めきる前に、この検証を先に通す。
